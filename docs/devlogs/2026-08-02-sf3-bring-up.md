# SF3 retail guest bring-up

## 2026-08-02 — dedicated workstream baseline

The SF3 port now has its own worktree, `I:\Projects\SF3-PC-Port`, and branch,
`research/sf3-full-bringup`, forked from SF2 Guest Runtime Alpha 10 commit
`001b1e8`. This preserves the proven shared PSX machine, renderer, audio,
input, disc and sequel-research foundation while keeping SF3 runtime ownership
separate from SF2.

The baseline recognizes the USA `SCUS-94640` executable and maps all 19
campaign resources. All mission packages construct through the native asset
diagnostics, all 360 compiled mission programs parse, and SF3-specific geometry
strides, TIM flags, overlay families, action descriptors, predicates, object
class `0x84`, XA groups and campaign boundaries are recorded in the existing
maps.

Retail guest gameplay is not yet running. The executable-entry probe passes
the earlier CD/GPU/BIOS boundaries and reaches BIOS event/SPU setup, then
enters an uninitialized guest target. The first implementation goal is a named,
instrumented SF3 bootstrap probe that identifies the target's producer and
executes continuously into the retail application loop. Native mission
construction remains research scaffolding and must not expand into a parallel
gameplay implementation.

The user-owned disc is indexed only in `.local-context/REFERENCE_INDEX.md`.
No disc bytes, extracted assets, RAM dumps, movies, audio, saves, or private
research material are tracked by Git.

The fresh baseline was reproduced from the dedicated worktree. Generic disc
inspection identifies `SCUS94640`, executable `SCUS_946.40`, entry
`0x800FB368`, text size `0x1CC000`, and the expected executable SHA-256.
`TOKYO` constructs with 16 FOG files, six virtual-root files, 40 world models,
33 texture files, 40 rooms, 270 objects, 49 definitions, and player source
199. The 5,000,000-instruction entry probe executes 4,979,172 guest
instructions and stops at `0x8016EA0C` with `ra` equal to the same address,
`sp=0x807FFDC8`, timer-1 mode `0x500`, CD interrupt flags
`0x2`/enable `0x7`, and SPU DMA registers
`0x1F6C14/0x560010/0x201`. These values are the initial named-bootstrap
regression signature; their presence does not yet explain the missing target.

`inspect-disc-info` reports that SF3 has no external selection catalog. That
command is an SF2 `DISK*.INF` view rather than an SF3 failure, so the local
baseline uses generic `inspect` and the checked-in executable mission table.

## 2026-08-02 — named executable-bootstrap probe

`sf_tool probe-sf3-guest-bootstrap` now owns the SF3 executable-entry
diagnostic. It rejects non-SF3 discs, preserves the 5,000,000-budget register,
timer, CD and SPU-DMA signature, and records a bounded 64-instruction final
control-flow window. The probe is observation-only: it does not patch the
guest target, force a BIOS result, or synthesize a completion event.

That window corrects the initial zero-target interpretation. The execution
result's instruction field is zero when the interpreter stops before fetching
the next budgeted instruction; guest RAM at `0x8016EA0C` actually contains
`0x1040FFFD`, a backward `beq`. The stable cycle is:

```text
0x8016EA04  jal   0x800FEFFC
0x8016EA08  nop
0x800FEFFC  lw    v0,0x814(gp)
0x800FF000  jr    ra
0x800FF004  sltiu v0,v0,1
0x8016EA0C  beq   v0,zero,0x8016EA04
0x8016EA10  nop
```

The named probe attributes the apparent `0x8016EA0C` transfer to the
`jr ra` at `0x800FF000` and the `$ra` producer to the `jal` at `0x8016EA04`.
With `gp=0x80121938`, the load polls word `0x8012214C`. Guest stores show its
initial zero written at `0x800FEEB8` (`sw zero,0x814(gp)`) and its blocking
value one written at `0x800FEFD4` (`sw v0,0x814(gp)`). No clear follows before
the budget expires. The immediate next investigation boundary is therefore
the producer/callback path around `0x800FEFD4` and the SPU-DMA/event completion
which should clear this word; it is not an uninitialized code dispatch.

## 2026-08-02 — continuous bootstrap reaches retail TITLE

The named probe now executes the retail SPU-DMA completion callback at
`0x800FF728`. Its store at `0x800FF734` produces the required software-state
transition at `0x8012214C`: `0 -> 1 -> 0`. The callback runs on a preserved
interrupt context; the host does not write the completion word.

SF3 also opens BIOS callback event class `0xF2000002`, spec `2`, mode `0x1000`
with callback `0x801078A4`. That address belongs to the sequel sound-service
family and does not clear the transfer word. Treating it as the DMA-completion
callback reproduced the stall and was rejected.

The next CD command exposed SF3's command-completion owner. The checked-in
structural map pairs SF2 callback `0x800F7008` with SF3 `0x800F9DD8`; binding
the latter to the existing CD INT2 service allows retail completion state and
callbacks to advance. The inherited callback stack `0x807F0000` was unsafe for
SF3 because its 2 MiB physical mirror is `0x001F0000`, where bootstrap assets
are live. A later TITLE.HOG read also overlapped the first replacement at
`0x807EF000`; the current callback stack is `0x8000B000`, below executable
text and outside both observed asset ranges.

With those two verified callback paths, the default 5,000,000-operation probe
now reaches `Game_Main` at `0x80029ED8`, enters the fourteen-state loop at
`0x80029FB8`, and follows sampled retail application states `0 -> 1 -> 4`.
State 4 owns the `TITLE.OVL` frame. A reproduced default run reaches depth 2,
one title-frame dispatch and 618 calls to the SF3 GPU-submission function at
`0x800F5B94`. A 100,000,000-operation stress run remains in stable state 4
with 101 title frames and 1,354 GPU submissions; it reports no CPU, memory or
alignment fault.

Disassembly of the SF3 push/pop and dispatcher paths independently establishes
the guest profile globals: current state `0x80121B88`, depth `0x80121B84`,
state stack `0x8010F304`, and transition byte `0x80121B8C`. These addresses,
the callback entries, the non-aliasing interrupt stack and the GPU boundary now
live in `Sf3GuestRuntimeProfile`; none are inherited from SF2.

The default probe treats that TITLE checkpoint as a regression gate and exits
nonzero if `Game_Main`, the state loop, state/depth `4/2`, the SPU completion,
a TITLE frame or a GPU submission is missing. Two independent complete runs
produce byte-identical 145-line diagnostics with SHA-256
`961714DD79B26CCB72E7B0D1E7F238A16CF8902ADCDDDEA11598ADF79E93CA6C`.

## 2026-08-02 — S2 title-shell boundary investigation

SF3 independently selects the verified sequel GPU DMA-chain decoder at the
presentation-only boundary. The retail submission is the call returning to
`0x800F458C`, not every entry at `0x800F5B94`. At 100,000,000 operations the
best captured TITLE frame is rooted at `0x801F8C94` with 25 packets, 54 GP0
words and eight draws.

The exact SF3 platform mappings now used by the diagnostic are CdSearchFile
`0x800FA688` and resident read `0x80026C7C`. Native delivery is restricted to
immutable ISO metadata/bytes: `TITLE.HOG` and the first 2 KiB catalog sector
of `MOVIE1.HOG`. Retail code parses the catalog, selects resident overlays and
owns application state. The catalog contains 27 entries and produces the
expected offsets; no proprietary bytes are written to the repository.

The first MDEC failure was downstream evidence, not an emulator wait-loop
bug. Without an STR frame, retail configured MDEC-output BCR with a zero block
count, which the hardware model expands to the maximum transfer and therefore
overwrites RAM. SF3's structurally matched decoder boundary is `0x80147660`;
its retail completion routine is `0x8002C930`. A headless-only handoff can
yield at the decoder, let MovieLoader return, and invoke that completion while
preserving the live guest continuation.

That handoff reveals an authored title playlist rather than a single stuck
movie: retail repeatedly selects catalog indices 21 through 25
(`DEMO1.STR`, `DEMO2.STR`, `SCEA.STR`, `TITLE.STR`, `ZINTRO.STR`). TITLE input
at `0x801565B4` accepts raw Start `0x0800` and transitions local states
`3 -> 0 -> 12`; presentation remains valid. The current blocker is the
playlist's retail input/skip boundary. Once playback begins, neither the
TITLE2 processed-PAD return `0x801597EC` nor the MENU return `0x8014DB80` is
reached, so immediately completing each clip only advances/loops the authored
playlist and cannot yet select Mission 1. This is not an S2 completion gate.

All runs in this slice used `sf_tool` only; no window was opened and no audio
device was used. `I:\Projects\PSX-References` remained read-only, and adopted
SF2 correspondences were independently checked against SF3 exact overlay or
structural maps.

## 2026-08-02 — S2 retail Mission 1 transition

TITLE input is state-gated rather than injected on a fixed wall-clock frame.
The probe waits for the mode-0 widget state to become four, confirms the
default item with Cross, and follows the story choice through title substates
`0 -> 10 -> 12 -> 11`. The other observed state-10 choices were independently
rejected as multiplayer routes: they load `TITLE2.OVL` with `MPTITLE.HOG` or
`MPTITLE2.HOG`, and the latter requests `FOG2/ARENA01.FOG`.

The story path exposed the exact retail memory-card prompts, including the
unformatted-card question. The probe now attaches an optional deterministic,
formatted blank 128 KiB card only for this SF3 diagnostic. Its A0 card calls,
B0 sector reads/writes and high/low completion events run through the existing
BIOS boundaries; SF1/SF2 callers retain the previous default. No save or card
image is persisted in the repository.

Title substate 11 initially looped in the CD/XA transition controller at
`0x800A6C8C`. The SF2 CFG load-delay report was evaluated as a lead, but this
probe executes the R3000 interpreter, whose ordinary-load delay regression
passes. Exact SF3 branch tracing instead showed successful `CdlGetstat` calls
whose response buffer remained `0x00`. The generic host-bound `CdControl` had
consumed the command IRQ without copying its response or publishing the PsyQ
completion reason. It now copies the controller response to the retail buffer
and records the actual interrupt reason (`CdlComplete == 2`) rather than the
old hard-coded disk-error value five. A focused Release regression covers the
response contract.

After that correction the retail shell tears down through application states
`4 -> 6 -> 0` and issues the exact disc requests
`\FOG\TOKYO.FOG;1` and `\TOKYO\SLF.RFF;1`. The bounded 500,000,000-operation
probe reaches a later mission heap boundary at `0x8016300C`; its failing store
follows an absent heap base after repeated `SLF.RFF` lookup/read attempts. That
is the next S3 archive/overlay bring-up problem, not a title-shell substitute
or a forced application-state write.

The successful run was headless and silent. Release
`sf_r3000_runtime_tests` passes, and the proprietary-data boundary remains
clean: disc bytes are read only from the user-owned image and temporary
diagnostic extracts remain outside the worktree.

The title-shell probe treats the observed Mission 1 request boundary as its
long-budget success gate while retaining the short TITLE regression gate.
Two clean 500,000,000-operation processes return zero with identical stdout
SHA-256 `8B67C9B4D8A050A5A53F80B61055ACEA58019667622BD0404CDCAB8E722E6A8F`;
stderr is empty. The complete configured Release suite passes 21/21.

## 2026-08-02 — TOKYO catalog and mission asset bring-up

The first post-S2 fault was caused by continuing the guest low-level sector
path after the probe had already host-owned the matching file/search boundary.
Delivering only the exact first 2 KiB sector of `TOKYO.FOG` lets SF3's retail
code build its own 20-entry virtual file table. This corrects the earlier
interpretation of `\TOKYO\SLF.RFF;1`: with the FOG catalog present, `SLF.RFF`
is not an ISO search at all. Retail resolves it from TOKYO and allocates the
exact `0x84800`-byte sound bank.

The immutable member bridge now follows the retail handle's file size and
per-handle offset. It supports the observed split `VLF.RFF` transfer
(`0x20000 + 0x5C000`) and resets its association whenever retail reuses the
five-slot handle pool for a different member. That reuse matters:
`WLDEMD.HOG` first supplies its 2 KiB catalog, then the same handle describes
the separate `TOKYO.SS` file. Treating the latter as a sequential HOG chunk
produced a deterministic unaligned pointer and was rejected.

The exact observed TOKYO-owned sequence is now:

```text
SLF.RFF      0x84800
TOKYO.DAT    0x01000
GENERIC.OVL  0x00800
VLF.RFF      0x7C000 (two reads)
DLF.RFF      0x34800
WLDEMD.HOG   0x00800 catalog read
TOKYO.SS     0x04800
NPC.HOG      0x00800 catalog read
```

After five exact SPU-DMA completions, retail application states advance
`0 -> 1 -> 4 -> 6 -> 0 -> 9 -> 3 -> 12 -> 0 -> 1`. The Mission 1 processed
PAD caller returns through `0x80050DA8`, and the presentation capture reaches
640 packets, 2,537 GP0 words and 625 draw commands. A 500,000,000-operation
run remains fault-free and bounded in guest CD/XA service with exact
`SCENES1.XA` and `TRASH.XA` searches. This is strong vertical-slice bring-up
evidence, but it is not yet an interactive product build.

Two parallel clean 500,000,000-operation processes both return zero, produce
empty stderr, and have identical stdout SHA-256
`422814CF91CCA5C6B3B294FC903CD6A8BCD361F9754677BBC808449D860E243C`.
The complete configured Release suite remains green at 21/21.

## 2026-08-03 — retail CD retry and stable Mission 1 gameplay entry

The two-sector Mission 1 stall was not the previously reported PSXRecomp CFG
load-delay defect. This path executes the R3000 interpreter, and its focused
ordinary-load delay regression remains green. The failing operation was an
eight-sector retail `CdRead` retry: six sectors completed, then the retry
issued `Setloc 02:00:00` instead of the requested `06:53:11` and left two
sectors pending.

Exact SCUS-94640 disassembly identifies the missing retail wrapper effects.
`CdControl` command 2 copies the requested four-byte location to
`0x8011FEA8` at `0x80106774`; command `0x0E` stores its mode in the following
byte at `0x8011FEAC`. The host-bound call had skipped both writes. The SF3
profile now supplies those independently verified mirror addresses to the
shared CD boundary, and the existing focused host-bound `CdControl` regression
continues to cover the Setloc/Setmode contract.

With the cached position restored, retail finishes Mission 1 initialization,
pushes application state 8 from `0x80163C28`, renders its loading/briefing
shell, and consumes one Cross sample from the processed PAD record. Its own
dispatcher tears down and pops state 8 at return `0x8002A67C`, producing the
full sampled path
`0 -> 1 -> 4 -> 6 -> 0 -> 9 -> 3 -> 12 -> 0 -> 1 -> 8 -> 0`.

An initially observed later state-7 menu was also diagnosed against SF3 rather
than assumed from SF2. The SCUS-94640 controller at `0x80050D48` obtains its
60-byte processed PAD record through `0x80022A60`, reads the button word at
`+4`, and pushes state 7 when stale frontend data contains Start `0x0800`.
Publishing a neutral host PAD record at the exact return `0x80050DA8` removes
that false pause transition. This is bounded input transport; retail continues
to own the player, pause decision and application stack.

The 150,000,000-operation Release gate now stops normally on its instruction
budget in application state `0`, depth `1`, after 201 state-0 display
submissions and 68 neutral gameplay PAD samples. It admits both observed XA
sectors, reports no rejected sector and no CPU, memory or alignment fault.
Two independent clean processes return zero with byte-identical stdout SHA-256
`89828E78A5CDE5CED232DA820A2B7C6DDD1D30D359A820A3A040B4DE235303A7`.
All runs were headless and silent; generated executable/disassembly material
and logs remained outside the worktree.
